# PageHeader — audit

Two defects, one component, found while composing an orders console rather than
while browsing a gallery. Both are visible below: the evidence renders live,
against the pristine design system on the left and our patched copy on the
right.

`components/ui/expanded/PageHeader.tsx` · Banhaten 0.3.0

---

## 1 · The description reorders its punctuation in right-to-left

**Severity:** major · **Status:** FIXED in `sandboxes/banhaten-proposed`

A Latin description inside an Arabic page renders with its final period at the
**front** of the sentence.

<Compare src="views/snippets/PageHeaderCase.tsx" dir="rtl" viewport={720} height={200} />

Look at the description line. Left: `.Refunds appear once…`. Right: the period
is back where it belongs.

**Why.** The `<p>` carries no `dir` attribute, so it inherits `rtl` from the
document while its content is Latin. A trailing `.` is bidi-neutral, and the
Unicode bidirectional algorithm moves it to the paragraph direction.

```diff
- <p className="ds-page-header__description">
+ <p className="ds-page-header__description" dir="auto">
```

The same one-line change applies to `ds-page-header__title`.

**This is the third instance of one root cause**, after `Table` and
`Breadcrumbs`. Banhaten's core components set `dir="auto"` on text they render —
39 occurrences. Everything under `expanded/` sets it twice. Those same four
files are also the only four of twenty-four with no `data-slot` attributes.

The patch is worth applying. The pattern is worth a conversation.

## 2 · Tab labels are clipped, and there is no way to opt out

**Severity:** major · **Status:** OPEN — this needs a design decision

<Compare
  src="views/snippets/PageHeaderCase.tsx"
  viewport={720}
  height={200}
  labels={['Pristine', 'Proposed (unchanged — not patched)']}
/>

The first tab reads `ll statuses`. It is not a font problem and not a rounding
error: every tab is exactly the same width regardless of its label.

| Label | Box | Text needs | |
| --- | --- | --- | --- |
| All statuses | 65.39px | 87.08px | clipped |
| Refunded | 65.41px | 68.58px | clipped |
| Pending | 65.41px | 62.00px | fits |
| Fulfilled | 65.39px | 59.23px | fits |

**Why — three rules combining.**

1. `PageHeader.tsx:153` hardcodes `fullWidth` on `<Tabs>`.
2. `.ds-tabs__tab { flex: 1 0 0px }` gives every tab an equal share of a zero
   basis, so width is `list ÷ count` and never content.
3. `.ds-tabs__label { flex: 0 0 auto; white-space: nowrap }` refuses to shrink,
   and the list's `overflow: auto` clips what spills.

**Two things make this worse than it looks.**

`Refunded` loses three pixels. That is small enough to survive review and large
enough to be wrong — the worst size a defect can be.

And there is no escape hatch. `PageHeaderTabs` is declared as

```ts
Pick<TabsProps, "activeIndex" | "ariaLabel" | "defaultActiveIndex" | "items" | "onActiveIndexChange">
```

`fullWidth` is not in that list, so a consumer cannot turn it off. `Tabs` does
set `ds-tabs--hug` when `fullWidth` is false — but **no CSS rule for that class
exists anywhere in the package.** The hug mode is a dead class.

**Not patched, on purpose.** Three reasonable fixes exist — let the label
truncate honestly, let the list scroll instead of clip, or expose `fullWidth`
through `PageHeaderTabs` — and they produce different products. Clipping the
first letter is the one outcome nobody chose, but choosing the replacement is
yours, not ours.
