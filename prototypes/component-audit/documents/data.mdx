# Data surfaces: `Table`, `PageHeader`, `pagination`

What a data surface prints, and what it looks like printing it. A count
nobody measured, labels that get cut, strings that exist but cannot be
reached — and two places where the surface disagrees with the system it is
built from.

---

## Table

### `table-1` · The footer prints a row count nobody measured

**Files:** `expanded/Table.tsx`, `pagination.tsx` · **Severity:** major
**Status:** Confirmed
**Repro:** frame `expenses`, the footer. Twelve rows are configured, ten to a
page, and the caption reads `Showing 1 to 10 of 20 results`, directly under the
table's own caption reading `Showing 1 to 10 of 12 rows`.

With `pagination={{ pageSize: 10, totalRows: 12, showCaption: true }}` the
footer renders two summaries that disagree, three pixels apart:

| Slot | Rendered |
| --- | --- |
| `toolbar-text` | `Showing 1 to 10 of 12 rows`, correct |
| `pagination-caption` | `Showing 1 to 10 of 20 results`, invented |

At three rows this read as two unrelated sentences — `1 to 3 of 3` beside
`1 to 10 of 20`, wrong on every number. At a page size closer to a real
product, the two now open identically, `Showing 1 to 10 of`, and diverge on the
one word that was never computed: `12 rows` against `20 results`. The more
realistic the page, the more the invented half reads as a typo in the total
rather than a caption that was never wired up.

`Pagination` has two text slots, `caption` and `summary`. `DataTable` passes
`summary` and never `caption`, so `caption ?? messages.caption` falls through to
the default.

That default is a demo string, hardcoded in `pagination.tsx`:

```ts
const defaultPaginationMessages: PaginationMessages = {
  caption: "Showing 1 to 10 of 20 results",
  ...
```

It counts nothing and never did. The Arabic set carries the same sentence
translated, so a localised table prints an equally invented count in Arabic.

**Why it matters.** A placeholder that looks like a placeholder gets caught. This
one is a well-formed sentence containing two plausible numbers, sitting in the
slot whose entire job is to report a quantity. It looked correct enough to ship,
and it is currently on screen under a caption reporting a different number.


Worth discussing: whether a default message should ever contain numbers. An empty
string fails visibly. This one failed quietly.

### `table-3` · A column with no `renderCell` prints nothing

**File:** `expanded/Table.tsx` · **Severity:** minor · **Status:** Question
**Repro:** frame `bills`. Every column there carries a `renderCell` because
three of them came back empty without one.

`TableColumn` requires `id` and makes both `renderCell` and `item` optional. So
this typechecks:

```ts
{ id: 'reference', header: 'Reference', width: 120, sortable: true }
```

It renders an empty cell for every row, even though `id` matches a key on the
row. The cell resolves `renderCell`, then `item`, then falls through to `null`.
There is no fallback to `row[column.id]`.

**Why it matters.** The column header appears, sorting works, the width is
respected. Everything about the column looks configured except the data, so the
first guess is that the rows are wrong rather than the column. We lost time to
exactly that.

**Two ways out, and they are different.** Falling back to `row[column.id]` when
both renderers are absent makes the obvious config work. Requiring one of them in
the type makes the mistake impossible. The second is stricter and would break
existing code that leans on empty columns as spacers.

### `table-4` · A sortable header ignores its own column's alignment

**Files:** `expanded/Table.tsx`, `expanded/table.css` · **Severity:** major
**Status:** Confirmed
**Repro:** frame `neon`. `id`, `price` and `stock` are configured
`align: "end"`. In every one of the three columns the header label sits at the
left edge and every value under it sits at the right edge — measured, in the
`price` column: the label spans 1977–2009px, the column box is 1965–2115px,
and `19.99` spans 2066.9–2103px. The label starts 12px from the left; the
value ends 12px from the right. 106px of the same 150px column separates them.

`TableColumn.align` is one value, typed for the whole column:

```ts
align?: "start" | "center" | "end";
```

Body cells honour it. `columnClass` turns `align: "end"` into
`ds-table__cell--end`, and `.ds-table .ds-table__cell--end { text-align: end }`
applies straight to the `<td>` — confirmed correct for RTL too, see
`index.mdx`'s "Alignment" entry.

The header cell carries the same class and the same `text-align: end`
computes on the `<th>`. It has no effect, because a sortable column's header is
not text — `Table` renders a `<Button className="ds-table__sort">` (or, when
`onSortChange` is absent, a `<span className="ds-table__sort ds-table__sort--static">`)
around the label and the sort icon, and `.ds-table__sort` is:

```css
.ds-table__sort {
  width: 100%;
  display: inline-flex;
  align-items: center;
  justify-content: flex-start;
  ...
}
```

`justify-content: flex-start` is unconditional — the rule carries no
`align`-scoped variant anywhere in `table.css`. A flex container's own
`justify-content` decides where its children sit; the parent `<th>`'s
`text-align` has nothing left to apply to. The column's alignment reaches the
`<th>` and stops there. This holds for `align: "center"` as well as `"end"`,
and for the non-interactive `--static` header (no `onSortChange`) exactly as
for the clickable one, since both share the one class.

Only a column with `sortable: false` escapes it: `Table` then prints
`column.header` as a bare string inside the `<th>`, which is text and does
follow `text-align`.

**Why it matters.** `align: "end"` on a numeric, sortable column is the
ordinary case for a data grid — ids, prices, quantities are exactly the
columns a product turns sorting on for. The header disagreeing with its own
data is not a rare configuration surfacing a rare bug; it is the default
combination, reproduced here on three of five data columns from one screen.

### `table-5` · `DataTable`'s search field cannot be narrowed

**Files:** `expanded/Table.tsx` (`DataTable`), `toolbar.tsx` (`ToolbarSearch`)
**Severity:** major · **Status:** Confirmed
**Repro:** frame `expenses`, with `search` configured and no `filters`. The
search field is the only child of its toolbar section and fills the row edge
to edge — measured at 2244px wide in a 2244px toolbar, in a screen whose own
reference puts a ~250px search box beside a Filter trigger and two chips.

`DataTable` renders its search field unconditionally as:

```tsx
<ToolbarSearch ... width="full" />
```

`width="full"` resolves to `w-full`. `table.css` also carries what reads like
a cap on the same element:

```css
.ds-data-table__toolbar [data-slot="toolbar-search"] {
  width: min(100%, var(--bh-input-width));
  flex: 1 1 min(100%, var(--bh-space-16xl-256));
}
```

It is not one. `flex-basis` is `min(100%, 256px)`, but `flex-grow: 1` on a
flex item with no growing sibling has nothing to share the row with, so it
grows past the stated `width` regardless — confirmed with `getComputedStyle`:
`width` computes to 2244px, not 320px, and `max-width` to `100%`, not a fixed
value. The same shape as `page-header-1`'s dead `ds-tabs--hug` class: a rule
that reads as a constraint and is inert in the layout mode it's declared for.

`DataTableSearch`, the type behind the `search` prop, exposes `defaultValue`,
`disabled`, `getRowText`, `label`, `onValueChange`, `placeholder`, `value` —
no `className`, no `width`. There is no prop path to a narrower search field
without abandoning `DataTable`'s own `search` and filtering rows yourself.

**Why it matters.** Every reference screen this project reproduces puts search
beside a filter trigger, filter chips, or a page action — never alone at full
width. `DataTable`'s only layout for a lone search field is the one layout no
real product on this canvas uses. `expenses` now routes around it: `rows` are
filtered in the view and the search field lives in a hand-built `Toolbar`,
which is more faithful to the reference but means `DataTable`'s own `search`
goes untested on this canvas — it is the only frame using `DataTable` at all.

## PageHeader

### `page-header-1` · It clips its own tab labels, with no way to opt out

**Files:** `expanded/PageHeader.tsx`, `tabs.tsx`, `tabs.css` · **Severity:** major
**Status:** Confirmed, needs a design decision rather than a patch
**Repro:** frame `bills`, the six tabs under the title.

Every tab gets the same width no matter what it says. On Xero's six tabs, in a
554px list, that width is 79.08px for all of them:

| Label | Box | Text needs | Result |
| --- | --- | --- | --- |
| All | 79.08 | 18.20 | **61px wasted** |
| Draft 13 | 79.09 | 54.44 | 25px wasted |
| Awaiting approval 1 | 79.08 | 136.11 | **57px short** |
| Awaiting payment 6 | 79.08 | 139.63 | **61px short** |
| Paid | 79.08 | 30.83 | 48px wasted |
| Repeating | 79.08 | 71.28 | fits |

The same row wastes 61px on `All` and starves `Awaiting payment 6` by 61px, at
the same time. Width has nothing to do with content.

And it does not clip here. The two long labels overflow their boxes and **print
on top of each other**, so the screen reads `Awaiting appro` with `Awaiti`
stamped through it. The earlier reading of this defect, on four tabs of similar
length, lost a letter. Six tabs of unequal length lose the sentence.

Three rules combine to produce it:

1. `PageHeader` hardcodes `fullWidth` on `<Tabs>`.
2. `.ds-tabs__tab { flex: 1 0 0px }`, so every tab takes an equal share of a zero
   basis. Width is `list ÷ count`, never content.
3. `.ds-tabs__label { flex: 0 0 auto; white-space: nowrap }` refuses to shrink,
   and the list's `overflow: auto` clips what spills.

**Why it matters.** The failure scales with tab count and with label length, and
nothing warns. A header that looked fine with four short tabs breaks the day
somebody adds a fifth or renames one, and the component gives no signal that it
has run out of room.

There is no escape hatch. `PageHeaderTabs` is
`Pick<TabsProps, "activeIndex" | "ariaLabel" | "defaultActiveIndex" | "items" | "onActiveIndexChange">`,
and `fullWidth` is not in the list. `Tabs` sets `ds-tabs--hug` when `fullWidth` is
false, but no CSS rule for that class exists anywhere in the package. The hug
mode is a dead class.

**Why we did not patch it.** Three reasonable fixes exist. Truncate the label
honestly, let the list scroll instead of clip, or expose `fullWidth`. They
produce different products. Clipping the first letter is the one outcome nobody
chose, but choosing the replacement is yours.

### `page-header-3` · Its action buttons draw the border twice

**File:** `expanded/pageHeader.css`, `expanded/PageHeader.tsx` · **Severity:** major · **Status:** Confirmed
**Repro:** frame `bills`. `Set up bill payments` and `New bill` sit in the
header; `Filter` and `Columns` sit in the toolbar below. All four are
`variant="secondary"`. The header pair has a visibly heavier edge.

`PageHeader` renders its own actions — `actions` takes descriptors, not
children, so a consumer never sees the `Button` and cannot style it. `Action`
renders `<Button variant="secondary" className="ds-page-header__action">`. The
variant is right. The class is the problem.

`Button`'s `secondary` draws its edge as an **inset** shadow, not a border:

```css
--shadow-button-secondary: inset 0 0 0 1px var(--bh-border-default), var(--shadow-button-surface);
```

`.ds-page-header__action` then adds a **real CSS border in the same token**, and
re-applies the same shadow beside it:

```css
border: 1px solid var(--page-header-border-default);  /* → --bh-border-default */
box-shadow: var(--shadow-button-secondary);           /* → the inset 1px, again */
```

An inset shadow paints from the padding edge inward, which begins immediately
inside the border. Two 1px lines of one colour, touching: **2px of solid
`--bh-border-default` where every other secondary button on the page has 1px.**
Nothing in the block resets either.

The size difference in the same screenshot is ours — the toolbar uses
`size="sm"` and the header's actions are 36px. That is a composition choice and
not part of this entry. The border is not: it is 2px against 1px at any size,
because the two lines are additive.

**Why it is more than 1px.** `.ds-page-header__action` does not adjust a button;
it re-declares one. Background, padding, radius, font size, font weight, line
height, height, colour and shadow are all restated against a parallel
`--page-header-*` token set. Some of those resolve to the same value today —
`--page-header-control-radius` is `--bh-control-default`, `--page-header-border-default`
is `--bh-border-default`. That is what makes it hard to see: the copy currently
agrees with the original almost everywhere, so only the one additive property
shows. A change to `Button`'s secondary variant will not reach these buttons,
and the next divergence will be as quiet as this one.

### `page-header-4` · It defeats the guard `Breadcrumbs` wrote against empty icons

**Files:** `expanded/pageHeader.css`, `expanded/breadcrumbs.css` · **Severity:** major · **Status:** Confirmed
**Repro:** frame `bills`, the `Purchases` crumb above the title. The breadcrumb is
passed `{ label, href }` and no icon. A 20×20 empty box sits before the label.

`Breadcrumbs` renders its icon slot unconditionally — `Breadcrumbs.tsx:82` emits
the `<span>` whether or not `item.icon` exists — and then guards it in CSS:

```css
.ds-breadcrumbs__icon:empty { display: none; }   /* breadcrumbs.css:84 */
```

That guard is correct and it works. Outside a `PageHeader`, an icon-less crumb
collapses to nothing.

`PageHeader` re-styles the same slot:

```css
.ds-page-header__breadcrumbs .ds-breadcrumbs__icon {   /* pageHeader.css:95 */
  width: var(--page-header-space-4xl);
  height: var(--page-header-space-4xl);
  display: inline-grid;
}
```

Both selectors weigh **(0, 2, 0)** — one class plus one pseudo-class against two
classes. A tie is broken by source order, `pageHeader.css` loads last, and
`display: inline-grid` beats `display: none`. The guard is not overridden by
something stronger; it loses a coin toss.

Measured in the DOM rather than inferred. The span reports `childNodes.length: 0`
and `matches(':empty') === true` — it really is empty — while computing a 20×20
box. Removing the one class and restoring it flips the outcome both ways:

| `.ds-page-header__breadcrumbs` on the `<nav>` | `display` | width |
| --- | --- | --- |
| present | `flex` | 20px |
| removed | `none` | 0px |
| restored | `flex` | 20px |

**Why it matters.** Every icon-less crumb inside a page header carries dead space
that the same component does not carry anywhere else, so the defect appears and
disappears with the container rather than with the markup. And the cost is not
the 20px: `Breadcrumbs` wrote a defence against exactly this state, and a sibling
component silently disabled it. Any future guard it writes at one class of
specificity is subject to the same coin toss.

This is `page-header-3` again with a different victim. There the parallel
`--page-header-*` declarations re-drew `Button`'s border; here they re-draw
`Breadcrumbs`' icon slot. One component reaching into two others, both times by
restating rules rather than composing.

## Pagination

### `pagination-1` · `DataTable` has nowhere to pass the Arabic messages

**Files:** `pagination.tsx`, `expanded/Table.tsx` · **Severity:** major
**Status:** Confirmed
**Repro:** frame `expenses-rtl`. Every string on that screen is Arabic except the
footer caption, which stays in English.

With a console fully translated and `dir="rtl"`, every string is Arabic except
the two in the table footer.

**The first version of this entry was wrong about the cause, and the registry is
what corrected it.** `banhaten docs pagination` is explicit:

> `messages`: **Direction does not select language.** English defaults are
> stable; pass messages for Arabic, Hebrew, Persian, Urdu, or another locale.

That is a deliberate and correct decision. Direction and language are different
axes, and an Arabic-direction interface may well be Hebrew or Persian. So
`Pagination` staying English under `dir="rtl"` is the documented behaviour, not a
defect, and "select messages from `dir`" is a fix that would work against the
stated design.

The defect is one step up. `Pagination` accepts `messages`. `DataTable` gives you
nowhere to pass them:

```ts
export type DataTablePagination = {
  ariaLabel?: string; defaultPage?: number; manual?: boolean;
  onPageChange?: (page: number) => void; page?: number; pageSize?: number;
  pages?: PaginationPage[]; showCaption?: boolean; totalRows?: number;
  type?: PaginationProps["type"]; variant?: PaginationProps["variant"];
};
```

No `messages`. `DataTable` has its own `labels` object covering the summary,
search placeholder and empty states, and it does translate — but it stops at the
footer caption, which comes from `Pagination`'s catalogue instead.

**Why it matters.** The package does the hard part and omits the seam.
`arabicPaginationMessages` is exported, complete, and unreachable from the
component most teams will actually use. A reader greps for Arabic support, finds
it, and concludes the component is covered.

### `pagination-2` · The active page is the same fill as the primary action

**File:** `pagination.tsx`, `globals.css` · **Severity:** minor · **Status:** Question
**Repro:** frame `expenses`. `Add expenses` sits at the top right and the active
page `1` at the bottom right, both in one viewport, both the same solid brand
fill.

This is not a slip, and it is not a coincidence of palette. The alias is direct:

```css
--bh-pagination-active-bg: var(--bh-interactive-brand-default);
```

That is the token `Button`'s `default` variant paints with. It is declared twice
in `globals.css`, once for each mode, and both point at the same place. No theme
overrides it. So in every theme and both modes, the current page and the page's
primary call to action are guaranteed to be the identical fill — by
construction, not by accident.

Both are also the only two saturated elements on the screen. The status badges
are soft-toned, the table chrome is neutral, and the pagination's own previous
and next controls are `soft`. Two solid brand rectangles at opposite corners,
and only one of them is asking for anything.

What makes this worth raising rather than shrugging at: **the seam already
exists and is already published.** `--bh-pagination-active-bg` appears by name in
`banhaten docs pagination`'s token contract, so the active fill can be
retargeted on its own without touching the brand token or the component API.
Nothing needs to be built for this to be adjustable — it already is.

No change is proposed here, and the question is a real one rather than a
rhetorical one. A current-page marker arguably *should* carry brand weight, and
plenty of systems do exactly this. The observation is only that the two roles are
locked to one value, and the lock is a default rather than a constraint.
