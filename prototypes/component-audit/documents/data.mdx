# Data surfaces: `Table`, `PageHeader`, `pagination`

Three findings about text a data surface prints. A count nobody measured, labels
that get cut, and strings that exist but cannot be reached.

*The patches are in `banhaten-proposed`. Run `banhaten diff` to see them.*

---

### `table-1` · The footer prints a row count nobody measured

**Files:** `expanded/Table.tsx`, `pagination.tsx` · **Severity:** major
**Status:** FIXED in `banhaten-proposed`

With `pagination={{ pageSize: 8, totalRows: 12, showCaption: true }}` the footer
rendered two summaries that disagreed:

| Slot | Rendered |
| --- | --- |
| `toolbar-text` | `Showing 1 to 8 of 12 rows`, correct |
| `pagination-caption` | `Showing 1 to 10 of 20 results`, invented |

`Pagination` has two text slots, `caption` and `summary`. `DataTable` passed
`summary` and never `caption`, so `caption ?? messages.caption` fell through to
the default string.

**Why it matters.** That default is a well-formed sentence containing two
plausible numbers, so it does not read as a placeholder. A table whose job is to
say how much data exists reported a quantity that was never measured, and it
looked correct enough to ship.

```diff
  showCaption={paginationConfig.showCaption ?? false}
+ caption={labels.resultsSummary({ from: visibleFrom, to: visibleTo, total: totalRows })}
  summary={labels.resultsSummary({ from: visibleFrom, to: visibleTo, total: totalRows })}
```

Worth discussing: whether a default message should ever contain numbers. An empty
string fails visibly. This failed quietly.

### `table-3` · A column with no `renderCell` prints nothing

**File:** `expanded/Table.tsx` · **Severity:** minor · **Status:** Question
**Repro:** frame `bills`. Every column there carries a `renderCell` because
three of them came back empty without one.

`TableColumn` requires `id` and makes both `renderCell` and `item` optional. So
this typechecks:

```ts
{ id: 'reference', header: 'Reference', width: 120, sortable: true }
```

It renders an empty cell for every row, even though `id` matches a key on the
row. The cell resolves `renderCell`, then `item`, then falls through to `null`.
There is no fallback to `row[column.id]`.

**Why it matters.** The column header appears, sorting works, the width is
respected. Everything about the column looks configured except the data, so the
first guess is that the rows are wrong rather than the column. We lost time to
exactly that.

**Two ways out, and they are different.** Falling back to `row[column.id]` when
both renderers are absent makes the obvious config work. Requiring one of them in
the type makes the mistake impossible. The second is stricter and would break
existing code that leans on empty columns as spacers.

### `page-header-1` · It clips its own tab labels, with no way to opt out

**Files:** `expanded/PageHeader.tsx`, `tabs.tsx`, `tabs.css` · **Severity:** major
**Status:** open, needs a design decision rather than a patch
**Repro:** frame `bills`, the six tabs under the title.

Every tab gets the same width no matter what it says. On Xero's six tabs, in a
554px list, that width is 79.08px for all of them:

| Label | Box | Text needs | Result |
| --- | --- | --- | --- |
| All | 79.08 | 18.20 | **61px wasted** |
| Draft 13 | 79.09 | 54.44 | 25px wasted |
| Awaiting approval 1 | 79.08 | 136.11 | **57px short** |
| Awaiting payment 6 | 79.08 | 139.63 | **61px short** |
| Paid | 79.08 | 30.83 | 48px wasted |
| Repeating | 79.08 | 71.28 | fits |

The same row wastes 61px on `All` and starves `Awaiting payment 6` by 61px, at
the same time. Width has nothing to do with content.

And it does not clip here. The two long labels overflow their boxes and **print
on top of each other**, so the screen reads `Awaiting appro` with `Awaiti`
stamped through it. The earlier reading of this defect, on four tabs of similar
length, lost a letter. Six tabs of unequal length lose the sentence.

Three rules combine to produce it:

1. `PageHeader` hardcodes `fullWidth` on `<Tabs>`.
2. `.ds-tabs__tab { flex: 1 0 0px }`, so every tab takes an equal share of a zero
   basis. Width is `list ÷ count`, never content.
3. `.ds-tabs__label { flex: 0 0 auto; white-space: nowrap }` refuses to shrink,
   and the list's `overflow: auto` clips what spills.

**Why it matters.** The failure scales with tab count and with label length, and
nothing warns. A header that looked fine with four short tabs breaks the day
somebody adds a fifth or renames one, and the component gives no signal that it
has run out of room.

There is no escape hatch. `PageHeaderTabs` is
`Pick<TabsProps, "activeIndex" | "ariaLabel" | "defaultActiveIndex" | "items" | "onActiveIndexChange">`,
and `fullWidth` is not in the list. `Tabs` sets `ds-tabs--hug` when `fullWidth` is
false, but no CSS rule for that class exists anywhere in the package. The hug
mode is a dead class.

**Why we did not patch it.** Three reasonable fixes exist. Truncate the label
honestly, let the list scroll instead of clip, or expose `fullWidth`. They
produce different products. Clipping the first letter is the one outcome nobody
chose, but choosing the replacement is yours.

### `pagination-1` · Arabic strings exist and nothing can reach them

**Files:** `pagination.tsx`, `expanded/Table.tsx` · **Severity:** major
**Status:** open

With a console fully translated and `dir="rtl"`, every string was Arabic except
the two in the table footer, which read `Showing 1 to 8 of 12 rows`.

This is a wiring problem, not a missing feature. `pagination.tsx` exports a
complete Arabic message set as `arabicPaginationMessages`. `DataTable` never
references it, with zero occurrences in the file. `Pagination` resolves its
strings as `{ ...defaultPaginationMessages, ...messageOverrides }` and nothing
consults `dir`. So `DataTable` passes `dir` down, the layout mirrors, and the
words stay English.

**Why it matters.** The work is done and the wiring is missing, which is the
failure mode most likely to survive review. A reader greps for Arabic support,
finds it, and concludes the component is covered. A team shipping an Arabic
console discovers by looking at the screen that they must hand-write every label,
including the caption `table-1` shows is wrong anyway.

Two candidate fixes, and they are not equivalent. Selecting messages from `dir`
inside `Pagination` makes RTL correct by default. Forwarding a `messages` prop
through `DataTable` makes it possible. The first is a behaviour change and
belongs to you.
