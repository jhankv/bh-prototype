# Notes — Banhaten component audit

Everything we have found, in one place, grouped by the component it is about.

**How an entry is named.** After its component, numbered in the order we found
it: `toolbar-1`, `checkbox-2`. A name tells you the subject before you read a
word, and it stays stable if the title gets reworded — which matters, because
entries cite each other.

**Where to see it.** Every entry names a **frame**. That name is the label above
the frame on the canvas.

| Frame | Reproduces | Components on it |
| --- | --- | --- |
| `mercury` | [Mercury — notification settings](https://mobbin.com/screens/cd614ddf-6c42-41be-b0ed-1e1a1653e70e) | `toggle` `badge` `menu` `input` `avatar` `button` |
| `neon` | [Neon — table browser](https://mobbin.com/screens/926541e1-1d12-4677-8faf-54193a709b17) | `checkbox` `select` `segmented-control` `toolbar` `Table` |
| `coda` | [Coda — document editor](https://mobbin.com/screens/d43c69b1-4c44-461a-8af9-4b9047d0ab0a) | `button-group` `tooltip` `menu` `select` |
| `import` | [PandaDoc — bulk import](https://mobbin.com/screens/6e7783c1-2ce2-4ba2-832d-bab89ec45f67) | `progress` `spinner` |
| `empty` | [Laravel Cloud — nothing created yet](https://mobbin.com/screens/5a0b71b3-f06f-4b14-af43-b862c1550a8f) | `EmptyState` |

Each has an `-rtl` twin rendering the same screen in Arabic.

Three frames are **galleries** rather than reproductions — `buttons`, `inputs`
and `inputs-proposed`. They show every variant of one component at once, which no
real screen does. Both instruments are needed and they find different things: a
gallery finds gaps in variant coverage, a composition finds disagreements
between components. `input-2` and `input-3` below came from a gallery and no
composition would have surfaced them, because a real form uses one variant per
field.

**Every screen is a faithful reproduction of a real product**, not a layout of
our own. That is deliberate: without it, any defect can be answered with "that
layout is not real". Where a screen needed something Banhaten does not ship —
navigation lists, prose, page tabs — that is plain markup, so a defect there
would be ours and not theirs.

Entries marked **Question** are not defects. They are places where more than one
answer is reasonable and the choice belongs to the design system's owners.

# Toolbar

### `toolbar-1` · It promises keyboard navigation and has none

**File:** `toolbar.tsx` · **Severity:** major · **Status:** open — one right answer
**Repro:** frame `neon`, the row above the filters. Tab into it, then press `→`.

`Toolbar` sets `role="toolbar"`. That role tells assistive technology two
specific things: the bar is **one** tab stop, and arrow keys move between the
controls inside it. Neither happens — the file contains no keyboard handler.

| | |
| --- | --- |
| Tab stops inside it | **10** |
| What the role promises | **1** |
| Arrow key from the first control | focus does not move |

**Why it matters.** A wrong role is worse than no role. Someone using a screen
reader is told arrow keys will work, tries them, nothing moves — and they cannot
tell whether the announcement was wrong or their own input was. With
`role="group"` they would simply Tab: slower, never misleading.

**This is not a feature request.** The component already claims this behaviour.
Adding the roving tabindex does not change what `Toolbar` is; it makes it do
what it says. It is the only entry here we would patch without asking.

Reference: [W3C ARIA Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/),
whose own worked example is a text formatting toolbar.

### `toolbar-2` · There is no separator

**File:** `toolbar.tsx` · **Severity:** minor · **Status:** Question — new API
**Repro:** frame `coda`, the two thin lines between the control groups.

A toolbar groups its controls and divides the groups with a rule.
[Radix ships `Toolbar.Separator`](https://www.radix-ui.com/primitives/docs/components/toolbar)
for this. Banhaten has no equivalent, so those two lines are hand-written spans.

They look right and are structurally wrong: a drawn line is invisible to
assistive technology, where a real separator announces that one group of
controls has ended and another has begun.

# ButtonGroup

### `button-group-1` · The container is a tab stop as well as every button

**File:** `button-group.tsx` · **Severity:** minor · **Status:** Question
**Repro:** frame `coda`, the formatting bar. Tab through it.

`ButtonGroup` renders `role="group"` with `tabIndex={0}` on the wrapper and
leaves every button inside focusable too. Tab stops on an empty container that
does nothing, then again on each button in it.

Measured on that bar: **11** tab stops, two of which are the containers
themselves — the one labelled "Text formatting" and the one labelled "Insert".

**Why we did not patch it.** Removing `tabIndex` from the wrapper changes the tab
order of every screen already using `ButtonGroup`. That is the same reason
`input-2` chose `aria-required` over the native `required` attribute: a fix that
silently changes behaviour for existing consumers is a decision, not a
correction.

# Architecture

### `architecture-1` · The two hand-built components are the two with keyboard gaps

**Files:** `toolbar.tsx`, `button-group.tsx` · **Status:** Question
**Repro:** frames `neon` and `coda`, both bars.

This is the entry worth reading first, because it explains the three above
rather than adding to them.

Nearly every interactive component in Banhaten wraps a Radix primitive —
`avatar`, `checkbox`, `dropdown-menu`, `select`, `switch`, `tabs` and `tooltip`
are all in `package.json`. **`@radix-ui/react-toolbar` and
`@radix-ui/react-toggle-group` are not.** Those two are written by hand.

And they are exactly the two with the gaps:

| | `role` | Arrow keys | One tab stop |
| --- | --- | --- | --- |
| `ToggleGroup` | `group` | yes — Bold → `→` → Italic | no |
| `ButtonGroup` | `group` | no — Link → `→` → stays on Link | no |
| `Toolbar` | `toolbar` | no handler at all | no |

`ToggleGroup` is the near miss: someone wrote the arrow keys, including the RTL
reversal, and stopped before the roving tabindex. Half the pattern is easy to
mistake for all of it.

**The question.** Adopting `@radix-ui/react-toolbar` would close `toolbar-1` and
`toolbar-2` together and bring the two outliers back in line with how the rest of
the package is built. Whether that is worth a dependency is an architectural
call, and it is the one we would most like answered.

# Table

*Recorded from the Sales Console composition, since removed. The fixes are in
`banhaten-proposed`; the screens that produced them are not on a canvas any more.*

### `table-1` · The footer prints a row count nobody measured

**Files:** `expanded/Table.tsx`, `pagination.tsx` · **Severity:** major
**Status:** FIXED in `banhaten-proposed`

With `pagination={{ pageSize: 8, totalRows: 12, showCaption: true }}` the footer
rendered **two summaries that disagreed**:

| Slot | Rendered |
| --- | --- |
| `toolbar-text` | `Showing 1 to 8 of 12 rows` — correct |
| `pagination-caption` | `Showing 1 to 10 of 20 results` — invented |

`Pagination` has two text slots, `caption` and `summary`. `DataTable` passed
`summary` and never `caption`, so `caption ?? messages.caption` fell through to
the default string in `pagination.tsx`.

**Why it matters.** That default is not a placeholder — it is a well-formed
sentence containing two plausible numbers. A table whose job is to say how much
data exists reported a quantity that was never measured, and it looked correct
enough to ship.

```diff
  showCaption={paginationConfig.showCaption ?? false}
+ caption={labels.resultsSummary({ from: visibleFrom, to: visibleTo, total: totalRows })}
  summary={labels.resultsSummary({ from: visibleFrom, to: visibleTo, total: totalRows })}
```

**Worth discussing:** whether a default message should ever be a sentence with
numbers in it. An empty string fails visibly; this failed silently.

### `table-2` · A name truncates from its start when its script opposes the document

**File:** `expanded/Table.tsx` (`avatarText` cell) · **Severity:** major
**Status:** FIXED in `banhaten-proposed`

The name and caption carried no `dir`, so both inherited the document direction.
`text-overflow: ellipsis` clips at the visual end of the line. When a string runs
opposite to the document, its *logical start* sits at the *visual end* — so the
ellipsis ate the beginning of the name.

| | Pristine | Proposed |
| --- | --- | --- |
| Name | `… de la Vega y Santibáñez` | `Maximiliano Alessandro …` |
| Email | `…e-procurement.example.com` | `maximiliano.alessandro.ferna…` |

**Why it matters.** A customer column exists to identify a person, and the
identifying part of a name is its beginning. In an Arabic-first system, an
operator running an English catalogue sees every long name arrive already
useless — and the cell still looks tidy, so nobody reports it.

Fix: `dir="auto"` on both, which gives each string its own base direction.

### `table-3` · It draws its own progress bar

**File:** `expanded/Table.tsx` · **Status:** Question

`expanded/Table.tsx` defines a local `Progress` component rather than using
`components/ui/progress.tsx`. Two implementations of one idea drift apart. Not
yet compared visually.

# PageHeader

*Also from the removed Sales Console.*

### `page-header-1` · It clips its own tab labels, with no way to opt out

**Files:** `expanded/PageHeader.tsx`, `tabs.tsx`, `tabs.css` · **Severity:** major
**Status:** open — needs a design decision, not a patch

`All statuses` rendered as `ll statuses` in LTR and `All statuse` in RTL. Every
tab was exactly `65.4px` wide regardless of its label:

| Label | Box | Text needs | Result |
| --- | --- | --- | --- |
| All statuses | 65.39 | 87.08 | clipped 21.7px |
| Refunded | 65.41 | 68.58 | clipped 3.2px |
| Pending | 65.41 | 62.00 | fits |
| Fulfilled | 65.39 | 59.23 | fits |

Three rules combining: `PageHeader` hardcodes `fullWidth` on `<Tabs>`;
`.ds-tabs__tab { flex: 1 0 0px }` gives every tab an equal share of a zero basis;
`.ds-tabs__label { flex: 0 0 auto; white-space: nowrap }` refuses to shrink, and
the list's `overflow: auto` clips what spills.

**Why it matters.** `Refunded` loses three pixels — small enough to pass review
and large enough to be wrong, which is the worst size for a defect. And it scales
with tab count: five tabs in a 391px header already breaks, with no warning.

**No escape hatch.** `PageHeaderTabs` is
`Pick<TabsProps, "activeIndex" | "ariaLabel" | "defaultActiveIndex" | "items" | "onActiveIndexChange">`
— `fullWidth` is not in the list. And `Tabs` sets `ds-tabs--hug` when `fullWidth`
is false, but **no CSS rule for that class exists anywhere in the package**. The
hug mode is a dead class.

**Why we did not patch it.** Three reasonable fixes exist — truncate the label
honestly, let the list scroll instead of clip, or expose `fullWidth` — and they
produce different products. Clipping the first letter is the one outcome nobody
chose, but choosing the replacement is yours.

### `page-header-2` · Title and description reorder punctuation in RTL

**File:** `expanded/PageHeader.tsx` · **Severity:** major
**Status:** FIXED in `banhaten-proposed`

The description rendered with its final period at the **front**:

```
.Every completed transaction across Retail, Online and Wholesale…
```

The `<p>` carried no `dir`, so it inherited `rtl` while its content was Latin. A
trailing `.` is bidi-neutral and gets reordered to the paragraph direction.

Fix: `dir="auto"` on both the title and the description.

**This is the third instance of one root cause**, after `table-2` and
`breadcrumbs-1`. See `architecture-2`.

# Pagination

### `pagination-1` · Arabic strings exist and nothing can reach them

**Files:** `pagination.tsx`, `expanded/Table.tsx` · **Severity:** major
**Status:** open

With a console fully translated and `dir="rtl"`, every string was Arabic except
the two in the table footer, which read `Showing 1 to 8 of 12 rows`.

**This is not a missing feature.** `pagination.tsx` exports a complete Arabic
message set as `arabicPaginationMessages`. `DataTable` never references it —
zero occurrences. `Pagination` resolves its strings as
`{ ...defaultPaginationMessages, ...messageOverrides }` and nothing consults
`dir`. So `DataTable` passes `dir` down, the layout mirrors, and the words stay
English.

**Why it matters.** The work is done and the wiring is missing, which is the
failure mode most likely to survive review: a reader greps for Arabic support,
finds it, and concludes the component is covered.

**Two candidate fixes, not equivalent.** Selecting messages from `dir` inside
`Pagination` makes RTL correct by default. Forwarding a `messages` prop through
`DataTable` makes it *possible*. The first is a behaviour change and belongs to
the design system team.

# Kbd

### `kbd-1` · Modifier and key swap order in RTL

**File:** `kbd.tsx` · **Severity:** major · **Status:** FIXED in `banhaten-proposed`

`<Kbd>⌘K</Kbd>` rendered as `⌘K` in LTR and as `K⌘` in RTL. `⌘` is a bidi-neutral
symbol, so the Unicode bidirectional algorithm reorders it to follow the
paragraph direction.

| | Pristine | Proposed |
| --- | --- | --- |
| `⌘K` | `K⌘` | `⌘K` |
| `⇧⌘P` | `P⌘⇧` | `⇧⌘P` |
| `Ctrl+S` | `Ctrl+S` | `Ctrl+S` |

Only shortcuts built from bidi-neutral glyphs are affected — `Ctrl+S` is correct
in both directions because those are strong LTR characters. So the bug hides
wherever a team writes shortcuts in ASCII and surfaces only on Apple modifiers.

**Why it matters.** A keyboard shortcut is not prose. `⌘K` is `⌘K` on every
keyboard in the world, including an Arabic one — the physical keys do not mirror.
An Arabic reader seeing `K⌘` is being told to press them in the wrong order.

Fix: `dir="ltr"` on the `Kbd` root.

### `kbd-2` · The defect is narrower than `kbd-1` first claimed

**File:** `kbd.tsx` · **Status:** narrowing, not a defect

The Sales Console rendered `⌘K` through `Input kind="shortcut"`, which uses
`KbdShortcut`. Measured in RTL: `⌘` at x=1036.7, `K` at x=1064.7 — correct order,
because pristine `kbd.tsx` already sets `dir="ltr"` on the `KbdShortcut` wrapper.

So `kbd-1` affects only **direct `<Kbd>⌘K</Kbd>` usage**, where the glyphs are children of the
`<kbd>` element itself. Anyone reaching for `KbdShortcut` or
`Input kind="shortcut"` was already safe.

This narrows the upstream report rather than widening it, and it is the kind of
correction only a composition produces — the gallery exercised `Kbd` directly and
never showed that the recommended path was already fine.

### `kbd-3` · The same reordering reaches a tooltip, where the fix does not

**Files:** `tooltip.tsx`, `kbd.tsx` · **Severity:** major
**Status:** open — observed, not yet written up in full
**Repro:** frames `coda` and `coda-rtl`, the tooltip held open under the bold button.

In `coda` the shortcut reads `⌘B`. In `coda-rtl` it reads **`B⌘`**.

`TooltipContent` renders its shortcut through `TooltipShortcut`, which is its own
`<span>` — **not** `Kbd`. So the `dir="ltr"` that fixes `kbd-1` does not reach
it. Same bidi mechanism, different component, and the fix does not travel.

# Badge

### `badge-1` · Two colour vocabularies for one idea

**Files:** `badge.tsx`, `expanded/Table.tsx` · **Status:** Question

`Badge` accepts `color`: `neutral · blue · green · amber · danger · purple ·
fuchsia · rose · sky · golden`. A badge cell inside `Table` accepts `tone`:
`blue · fuchsia · amber · neutral · success · warning · danger`.

`green` and `golden` are missing from the second; `success` and `warning` from
the first. `expanded/Table.tsx` bridges them with a private `badgeColor()`
mapping `success → green`, `warning → amber`.

It renders correctly. The cost is that whoever learns one vocabulary guesses
wrong in the other, and neither type says so.

### `badge-2` · An invalid colour renders an unstyled badge instead of failing

**File:** `badge.tsx` · **Severity:** minor

Passing anything outside the union — `red` is the obvious guess for a failure
state — produces a badge with no background, no border and no padding. It renders
as bare text that does not read as a badge at all.

In TypeScript the mistake is caught; in a JS codebase, or when the value arrives
from data, it ships silently, and a status column quietly loses its most
important state.

**Suggested:** give `badgeVariants` a `defaultVariants.color` of `neutral`, and
warn in development naming the invalid value and the valid set.

### `badge-3` · Five order statuses, four badge tones

**Files:** `badge.tsx`, `expanded/Table.tsx` · **Status:** Question

`partially refunded` has no tone of its own and falls back to `neutral` — the
same tone as `refunded`. Two different states render identically.

Only a gap if the tone set is meant to be exhaustive, which is worth asking.

# Input

### `input-1` · `shortcutKeys` is silently ignored unless `kind="shortcut"`

**File:** `input.tsx` · **Status:** Question

`shortcutKeys` lives on `InputModeRenderProps`, which is intersected into
**every** kind variant. So `<Input shortcutKeys={['Mod','K']} />` typechecks,
passes lint, and renders nothing. Cost one debugging cycle.

Making the shortcut props exclusive to `kind: "shortcut"` would turn a silent
no-op into a compile error.

### `input-2` · `isRequired` is decorative, and assistive technology is told nothing

**File:** `input.tsx` · **Severity:** major
**Status:** FIXED in `banhaten-proposed`
**Repro:** frames `inputs` vs `inputs-proposed`, the label and helper text group.

`isRequired` drew an asterisk carrying `aria-hidden="true"`, and the control set
`required` from the **native** prop only — `isRequired` never reached the input.
Measured on the rendered field: `required` absent, `aria-required` absent,
asterisk hidden. A screen reader announced "Email, edit text" and nothing more.

The one visual signal that the field is mandatory was the one piece explicitly
hidden from the accessibility tree.

```diff
+ aria-required={isRequired || required || undefined}
  required={required}
```

**There is no figure for this one, and there cannot be.** The fix is an
attribute; nothing on screen changes. Measured instead, on the `isRequired`
field of frames `inputs` and `inputs-proposed`:

| | Pristine | Proposed |
| --- | --- | --- |
| `aria-required` | absent | `"true"` |
| Announced | "Email, edit text" | "Email, edit text, required" |

That invisibility is the finding, not a caveat about it. A sighted user sees the
asterisk either way; the person the asterisk was drawn for was told nothing.

`aria-required` rather than native `required` **on purpose**: adding the native
attribute would switch on browser form validation and change behaviour for every
existing consumer. This states the fact without changing the mechanics.

### `input-3` · `isOptional` renders nothing unless `optionalText` is also passed

**File:** `input.tsx` · **Severity:** minor
**Status:** FIXED in `banhaten-proposed`
**Repro:** frames `inputs` vs `inputs-proposed`, the label and helper text group.

The optional marker was gated on both the flag and the text, and `optionalText`
had no default. So `<Input label="Company" isOptional />` rendered a label
indistinguishable from one with no flag at all.

The asymmetry is the tell: `isRequired` alone draws its asterisk, `isOptional`
alone draws nothing.

<Compare src="views/snippets/InputOptionalCase.tsx" viewport={620} height={110} />

Middle field, top line. Pristine says `Company`; patched says `Company
(optional)`. Same file, same props, one sandbox apart.

Fix: `optionalText ?? (isOptional ? "(optional)" : undefined)`.

**Open question.** The default string is English. In an Arabic-first system that
arguably belongs in the locale layer, not the component.

# Avatar

### `avatar-1` · Initials are not meaningful for Arabic names

**File:** `avatar.tsx` · **Status:** Question

The initials fallback takes the first letter of the first two words:

| Name | Initials |
| --- | --- |
| عاشور عوضية | عع |
| سفيان تومي | ست |
| عبد الرحمن بن محمد بن عبد الله آل سعود الشمري | عا |

Two problems. Arabic script is cursive, so isolated letters lifted out of a word
render in forms a reader does not associate with the name. And initials are not
an Arabic naming convention at all — `عع` carries no identifying signal, while
`ست` happens to read as an unrelated word.

Compounding it, Arabic given names are heavily concentrated (عبد, محمد, أحمد), so
first-letter initials collide constantly. Three different customers in one
dataset all showed `عا`.

**Not filed as a defect** because there may be no good answer. Options worth
discussing: fall back to a generated colour or icon when the name is non-Latin,
or drop initials entirely.

# Architecture, continued

### `architecture-2` · The `expanded/` family did not inherit the bidi convention

**Files:** everything under `expanded/` · **Status:** Question

`table-2`, `breadcrumbs-1` and `page-header-2` looked like three defects. They
are one.

**The first hypothesis was wrong.** A first pass suggested Banhaten had no bidi
isolation anywhere. That search ran from the wrong directory and returned
nothing. The real count:

| | `dir="auto"` occurrences |
| --- | --- |
| Core components | **39** |
| `expanded/` | **2** (both in `EmptyState`) |

So this is not a missing concept. Banhaten applies the correct pattern throughout
its core and the team clearly knows it. The gap is that the `expanded/` family —
`Table`, `Breadcrumbs`, `PageHeader` — was authored without it.

Those same four files are also the only four of twenty-four with no `data-slot`
attributes.

**That reframes the report.** It is not "please learn about bidi". It is "your own
convention did not reach these four files." `expanded/` is a second-class citizen
of this design system, and that is the finding worth sending upstream — not three
separate patches.

# Verified good

Checked deliberately and found correct, so nobody re-checks them.

- **RTL layout**: column order, header sort affordances, filter chips, search
  field and its icon, pagination controls, toolbar, page header actions and
  breadcrumbs all mirror correctly.
- **Theming**: `brown` and `sharp` change brand colour and corner radius with
  nothing hardcoded leaking through.
- **Dark mode**: status colours, row separators and surfaces all hold.
- **Arabic typography**: IBM Plex Sans Arabic loads and renders correctly at
  table density.
- **Alignment**: `align: "end"` correctly resolves to the left edge in RTL for
  numeric columns.
- **Already carrying `dir="auto"`**: `tag`, `badge`, `button`.

# Investigated and rejected

Knowing what is *not* broken is what keeps this report credible.

- **Currency renders as `$US ١٢٬٤٨٠٫٥٠` in RTL, not `US$ …`.** Not a defect.
  `Intl.NumberFormat("ar-EG")` emits the mark, then digits, then `US$`, and `$`
  is bidi-neutral, so the Unicode algorithm correctly places it left of `US` in
  an RTL paragraph. Verified by reading the raw code points. This is correct RTL
  presentation.

# Not covered, and why

- **`table-elements`** exports structural wrappers with almost no styling —
  `TableCell` and `TableBody` add no classes at all. A screen built on them would
  be showing our CSS, so any defect found would be ours. It belongs to the code
  pass.
- **A caution for that pass.** `useDS()` returns components typed as
  `ComponentType<Record<string, unknown>>`, so an invalid prop typechecks cleanly
  inside a prototype. `ToolbarButton variant="brand"` was written here and did
  nothing — `brand` is not one of its variants. No claim about a prop may come
  from a prototype compiling; only from reading the component.
