# Forms: `input`, `badge`, `checkbox`, `select`, `avatar`, `button`, `menu`

Flags that render nothing, values that fail silently, and contracts
narrower than the code behind them.

## Input

### `input-1` · `shortcutKeys` is quietly ignored unless `kind="shortcut"`

**File:** `input.tsx` · **Status:** Question
**Repro:** frame `empty` shows the working path — `kind="shortcut"` together with
`shortcutKeys`. Drop the `kind` and the keys vanish with no error. That is the
whole finding, so the frame is the control rather than the defect.

`shortcutKeys` lives on `InputModeRenderProps`, which is intersected into every
kind variant. So `<Input shortcutKeys={['Mod','K']} />` typechecks, passes lint,
and renders nothing. It cost us one debugging cycle.

The documentation is not at fault here. `banhaten docs input` states the coupling
in the prop table — "For `kind="shortcut"`, renders one compact, platform-aware
Shortcut chip" — and `USAGE.md` says to reach for `shortcutKeys` or `KbdShortcut`
rather than hard-coding a glyph. Anyone who reads the docs gets this right.

The finding is only that the type does not encode what the prose says. Making the
shortcut props exclusive to `kind: "shortcut"` would turn a silent no-op into a
compile error, and would carry the documentation into the editor.

### `input-2` · `isRequired` is decorative, and assistive technology hears nothing

**File:** `input.tsx` · **Severity:** major · **Status:** Confirmed
**Repro:** frame `inputs`, the label group. The asterisk beside a required label
carries `aria-hidden="true"`; read the control's attributes and no `required` or
`aria-required` is present unless the native prop was passed too.

`isRequired` drew an asterisk carrying `aria-hidden="true"`, and the control set
`required` from the native prop only. `isRequired` never reached the input.

There is no figure for this one, and there cannot be. The fix is an attribute, so
nothing on screen changes.

| | Renders as | Should read |
| --- | --- | --- |
| `aria-required` | absent | `"true"` |
| Announced | "Email, edit text" | "Email, edit text, required" |

That invisibility is the finding. A sighted user sees the asterisk either way,
and the person it was drawn for was told nothing.

```diff
+ aria-required={isRequired || required || undefined}
  required={required}
```

We used `aria-required` rather than the native `required` on purpose. The native
attribute switches on browser form validation and would change behaviour for
every existing consumer. This states the fact without changing the mechanics.

### `input-3` · `isOptional` renders nothing unless `optionalText` is also passed

**File:** `input.tsx` · **Severity:** minor · **Status:** Confirmed
**Repro:** frame `inputs`, the label group. `isOptional` alone renders no row at
all, so the flag looks like it did nothing.

The optional marker was gated on both the flag and the text, and `optionalText`
had no default. So `<Input label="Company" isOptional />` rendered a label
indistinguishable from one with no flag at all.

The asymmetry is the tell. `isRequired` alone draws its asterisk; `isOptional`
alone draws nothing. Either the flag means something by itself or it should not
exist.

<Specimen src="views/snippets/InputOptionalCase.tsx" viewport={620} height={150} />

Three fields, one row. The first carries `isRequired` and draws its asterisk. The
second carries `isOptional` and draws nothing at all. The third adds
`optionalText` and the row finally appears. Same component, same label.

The render guard is `isOptional && hasRenderableContent(optionalText)`, and
`selectedOptionalText` is `optionalText` with no fallback. So the flag alone
cannot produce the row it names.

One thing to decide: the default string is English. In an Arabic-first system it
arguably belongs in the locale layer rather than the component.

### `input-4` · The focus ring is twice the floor and drops the border it replaces

**File:** `input.tsx`, `globals.css` · **Severity:** minor · **Status:** Question
**Repro:** frame `inputs`, the `default` field. Click into it. Same in frame
`neon`, the search field above the grid.

This is not a contract violation, and it is recorded so nobody spends an hour
deciding whether it is one. The ring is systematic, token-driven, and passes
WCAG. It is a question of visual weight, and the choice is Banhaten's.

The mechanism, measured rather than eyeballed. Three controls, one width token:

| Control | Primitive | Blue band | Offset |
| --- | --- | --- | --- |
| `Button` | `--shadow-component-focus-ring` | 4px | flush |
| `Input` | `--shadow-component-focus-stroke` | 4px | 1px |
| `Select` | `--shadow-component-focus-stroke` | 4px | 1px |

`--bh-focus-ring-width` is `4px` and `--bh-border-width-default` is `1px`, so
`focus-stroke` paints a 1px ring in `--bh-bg-default` and then 4px of
`--bh-border-focus` outside it. Buttons flush, fields offset, is a coherent rule:
a field already has a border and the gap stops the two merging.

Two things then compound. The 1px gap is `bg-default`, which on a white surface
is white — so the gap is invisible and the ring reads as a solid band sitting on
the field edge. And `input.tsx` sets `--shadow-input-focus-overlay: none` on
focus, which removes the field's own 1px border for as long as it is focused.
The edge does not gain a ring; it is replaced by one.

WCAG 2.2 SC 2.4.13 asks for at least a 2px perimeter at 3:1. 4px is double that,
so the floor is not the constraint here. For comparison, shadcn/ui's current
input uses `focus-visible:ring-[3px]` with `ring-ring/50` and
`focus-visible:border-ring` — a narrower band, at half opacity, with the border
recoloured rather than removed. Both pass. Banhaten's is 33% wider, at twice the
opacity, and replaces the border instead of keeping it.

No fix is proposed, and none should be read into the comparison. The observation
is only that three independent decisions — width, opacity, and dropping the
border — all push the same direction at once, and the result reads heavier than
the system likely intends.

### `input-5` · The field is 320px wide and its container cannot widen it

**File:** `input.tsx`, `globals.css` · **Severity:** minor · **Status:** Question
**Repro:** put an `Input` in any container wider than 320px — a grid column, a
two-column form, a centred header search. It stays 320.

`inputRoot` is `cva("grid w-[var(--bh-input-width)] max-w-full")` at
`input.tsx:97`, and `--bh-input-width` resolves to `320px`. `max-w-full` clamps
the field **down** inside a narrower parent; nothing lets it grow. So a field's
width is a property of the component, not of the space it is given.

The published contract does not say so. The prop table carries `density` and
`size` for height and nothing at all for width, and while `--bh-input-width` is
listed among the tokens, a token is a theme-wide value, not a per-instance
control. A reader of the contract has no way to learn that the field will ignore
its container.

There is a way out, and it is not in the contract either: `input.tsx:373` merges
the consumer's `className` through `twMerge`, so `className="w-full"` beats the
arbitrary `w-[var(...)]` and the field fills its parent. That is the shadcn
escape hatch working as designed — but it is the escape hatch, reached for a case
the props do not cover.

The reason this reads as a question rather than a preference is that the system
is not consistent with itself about it. `MenuContent` publishes `width` as a
prop, so width-as-a-prop is a shape Banhaten already uses. `Input` is the wider
of the two surfaces and publishes none.

Two readings, and only Banhaten can pick. Either 320px is the field's designed
width and `className` is the accepted way to depart from it — in which case the
docs should say so, because nothing currently does. Or a form primitive is meant
to fill the space it is handed, and the fixed width is the part that is wrong.

## Badge

### `badge-1` · Three colour vocabularies for one idea

**Files:** `badge.tsx`, `expanded/Table.tsx` · **Status:** Question
**Repro:** frame `specimens`, the two badge rows. The bottom table asks a `Table`
badge cell for all ten `Badge` colours. All ten render — which is the finding,
because five of them are a type error to write.

Three lists describe the same idea and none of them matches another.

| | Count | Values |
| --- | --- | --- |
| Design tokens | 11 | `amber` `aqua` `blue` `fuchsia` `golden` `green` `lime` `purple` `red` `rose` `sky` |
| `Badge` `color` | 10 | `neutral` `blue` `green` `amber` `danger` `purple` `fuchsia` `rose` `sky` `golden` |
| `Table` badge cell `tone` | 7 | `blue` `fuchsia` `amber` `neutral` `success` `warning` `danger` |

**`aqua` and `lime` exist as tokens and no component exposes them.** They are
defined and themed and unreachable through any public API.

**`red` is named `danger` in `Badge`.** The token behind it is
`--bh-bg-accent-red-subtle`.

**The `tone` type is narrower than the code behind it.** `badgeColor()` special
cases `success` and `warning`, then forwards everything else untouched:

```ts
function badgeColor(tone: BadgeItem["tone"]) {
  if (tone === "success") return "green" as const;
  if (tone === "warning") return "amber" as const;
  return tone ?? "neutral";
}
```

So `tone: "purple"` renders a correct purple badge and fails to compile. Five
hues behave this way. The type is the only thing stopping them, and it is
stopping them by accident — the declared union simply lists fewer values than the
function passes through.

**Why the naming matters.** None of it is guessable, and a wrong guess does not
fail — see `badge-2`. Asked to name the colours from memory, our own designer
reached for `purple`, `pink`, `teal` and `yellow` after a week inside the system.
One of the four exists. `pink` is `fuchsia` or `rose`; `teal` is `aqua` or `sky`;
`yellow` is `amber` or `golden`.

`Badge` also still accepts a legacy `variant` prop (`success`, `destructive`,
`soft-warning`, and nine more). That is not part of this finding: the registry
documents it as a compatibility shim, which is a reasonable thing to keep.

### `badge-2` · An invalid colour renders an unstyled badge instead of failing

**File:** `badge.tsx` · **Severity:** minor
**Repro:** frame `specimens`, the Badge colours row. The last badge is `red` and
renders with a transparent background beside five that do not.

Passing anything outside the union produces a badge with no background, no
border and no padding. It renders as bare text that does not read as a badge at
all. `red` is the obvious guess for a failure state, and it is not in the union.

TypeScript catches the mistake. A JS codebase, or a value arriving from data,
does not, and a status column quietly loses its most important state.

## Checkbox

### `checkbox-1` · A white tick on a white box, in two of the seven themes

**File:** `checkbox.tsx`, `select.tsx`, `globals.css` · **Severity:** major · **Status:** Open
**Repro:** frame `neon`. Set the toolbar to dark mode and the `gray` theme, then
tick a row. The box fills near-white and the tick vanishes into it.

Measured on the checked control: surface `#FAFAFA`, tick `#FFFFFF`, **1.04:1**.
WCAG 2.2 SC 1.4.11 asks for 3:1 on a graphical object you need in order to
understand the state, and a checkbox's tick is the entire state.

The cause is two tokens defined one line apart, only one of which is aware of
the theme:

```css
/* globals.css, light */
466  --bh-content-on-brand: var(--bh-colors-brand-color-on-brand-light);
467  --bh-content-on-color: var(--bh-base-white);

/* globals.css, dark */
2296 --bh-content-on-brand: var(--bh-colors-brand-color-on-brand-dark);
2297 --bh-content-on-color: var(--bh-base-white);
```

`on-brand` resolves through a per-theme, per-mode value. `on-color` is white in
every theme and in both modes.

The checked surface is `--bh-interactive-checkbox-default`, and in dark it takes
each theme's own `-dark` value — for `gray` that is `--bh-gray-50`, `#FAFAFA`.
Nothing about that is wrong on its own: a light control on a dark page is the
correct call. What never happens is the ink following it.

The system already knows how to do this, which is what makes it a defect rather
than a gap. `Button`'s default variant sits on `--bh-interactive-brand-default`
and takes `--bh-content-on-brand`. Measured on the same page, in the same theme
and mode as the invisible tick above: `#FCFCFC` on `#0E0E0F`, **18.81:1**. Two
controls on the same near-white brand surface, and only one of them flips.

All fourteen combinations, tick against checked surface:

| Theme | Light | Dark |
| --- | --- | --- |
| `blue` | 5.44 | 4.06 |
| `gray` | 17.40 | **1.04** |
| `brown` | 3.96 | 3.96 |
| `orange` | 7.31 | **2.26** |
| `green` | 5.48 | 4.62 |
| `purple` | 7.10 | 5.70 |
| `teal` | 5.47 | 4.68 |

Two fall under the 3:1 floor and both are in dark mode. `gray` is unusable.
`orange` at 2.26 is only as legible as it is because `#FB923C` happens to be
mid-toned; it is the same failure with a kinder accident.

`select.tsx:894` repeats the pairing for the multi-select tick, over the same
`--bh-interactive-checkbox-default`, so it fails in the same two themes.

The token is not at fault everywhere, and that is worth stating so it is not
blamed wholesale. `badge.tsx` pairs `--bh-content-on-color` with
`--bh-bg-accent-*` and `button.tsx` pairs it with
`--bh-interactive-danger-default` — fixed hues that do not move with the theme,
where a constant white is a correct constant. `Checkbox` is the only component
that puts it over a surface that does move.

## Select

### `select-1` · A label-less select announces its value and has no name

**File:** `select.tsx` · **Severity:** major · **Status:** Confirmed
**Repro:** frame `neon`. Every select there is label-less. Read the trigger's
`aria-label`: it is `stock`, `gte`, `50`, `0` — the value, never the purpose.

`Select` derives the trigger's accessible name from its own selection:

```ts
const triggerAccessibleLabel = shouldRenderLabel
  ? undefined
  : getAccessibleText(selectedValue) ?? getAccessibleText(selectedPlaceholder)
```

With a visible `label` the name comes from the label, which is correct. Without
one — a toolbar, a filter row, anywhere a visible label would be noise — the name
becomes the current value.

**A value is not a name.** Someone tabbing Neon's filter row hears "stock,
button", "gte, button", "15", "50, button". Four controls, four values, and
nothing saying which is the field, which is the operator, which is the page size.
Change the selection and the control's name changes with it.

**The consumer cannot fix it, and that is the sharper half.** `aria-label` passed
to `Select` does not reach the trigger. `{...props}` is spread on the outer
`SelectRoot`, and the trigger takes `aria-label={triggerAccessibleLabel}`
explicitly, so the value wins. Measured on this screen: the two
`aria-label="Rows per page"` and `aria-label="Offset"` we passed landed on
`<div data-slot="select-root">` — a plain div with no role, where no screen
reader will ever read them.

So the API offers exactly two states: a visible label, or no name at all. There
is no third option, and a filter bar needs one.

The calls in `views/TableStudio.tsx` still pass `aria-label`. They are left in
deliberately: they are what a careful team writes, and they are what silently
does nothing.

## Avatar

### `avatar-1` · Initials are not meaningful for Arabic names

**File:** `expanded/Table.tsx`, its local `Avatar` · **Status:** Question
**Repro:** frame `specimens`, the Arabic names table.

The derivation is not in `avatar.tsx`. `AvatarFallback` renders whatever children
it is given; the initials are computed by a private `Avatar` inside
`expanded/Table.tsx`, which is the only place this happens.

The fallback takes the first letter of the first two words:

| Name | Initials |
| --- | --- |
| عاشور عوضية | عع |
| سفيان تومي | ست |
| عبد الرحمن بن محمد بن عبد الله آل سعود الشمري | عا |

Arabic script is cursive, so isolated letters lifted out of a word render in
forms a reader does not associate with the name. Initials are also not an Arabic
naming convention. `عع` carries no signal, and `ست` reads as an unrelated word.

Arabic given names are heavily concentrated (عبد, محمد, أحمد), so first-letter
initials collide constantly. Three different customers in one dataset all showed
`عا`.

We did not file this as a defect because there may be no good answer. Worth
discussing: fall back to a generated colour or icon when the name is non-Latin,
or drop initials entirely.

## Button

### `button-1` · Five of fourteen variants are not in the published contract

**File:** `button.tsx` · **Severity:** major · **Status:** Confirmed
**Repro:** frame `buttons`, the variant grid. `danger` and `destructive` sit two
apart and are the same red; so do `soft-danger` and `soft-destructive`.

`banhaten docs button` publishes nine variants:

> `default`, `secondary`, `soft`, `outline`, `ghost`, `ghost-primary`, `danger`,
> `soft-danger`, `white`

`buttonVariants` defines fourteen. The five it does not publish fall into two
groups, and they are not the same problem.

**Two are undeclared aliases.** `destructive` and `soft-destructive` are
byte-identical to `danger` and `soft-danger` — 359 and 474 characters, compared
literally, not by eye. Same tokens, same hover, same focus shadow, same disabled
state. Nothing in 103 lines of documentation mentions either name, and the only
occurrence of the word "destructive" is prose describing the use case:
"navigation actions, and destructive confirmations."

**Three are simply unpublished.** `success`, `warning` and `link` are distinct
from everything else and appear nowhere in the contract, so a consumer reading
the docs cannot discover that they exist.

Both groups reach the consumer the same way. `VariantProps<typeof
buttonVariants>` derives from the implementation, so all fourteen typecheck and
all fourteen autocomplete. The docs say nine. Whichever a team reads first is
the API it gets, and two teams can ship two names for one button with nothing
marking which is canonical — or a deprecation path if the alias is later removed.

What makes this a defect rather than a preference is that **Banhaten already has
a convention for exactly this, and Button does not follow it.** `banhaten docs
badge` declares its own aliases:

> `legacyVariants`: The previous variant prop is still accepted as a
> compatibility shim.

That declaration is why `badge`'s identical situation is recorded above as *not*
a finding. Button's own `density` prop is documented the same careful way —
"Maps to legacy xs, sm, or default sizes." The vocabulary to describe a
compatibility alias exists, is used twice elsewhere in this component's own
documentation, and is absent from its variants.

### `button-2` · A leading icon and a trailing label are padded in opposite directions

**File:** `button.tsx` · **Severity:** minor · **Status:** Confirmed
**Repro:** frame `bills`, the `Columns` button in the toolbar. Ink to the left
edge, 7.25px. Ink to the right edge, 10.68px. Same button, same padding value on
both sides.

`padding` is symmetric — 6px each side. Two other rules are not, and they point
opposite ways.

```css
--bh-button-icon-offset:    calc(var(--bh-space-xxs-2) * -1);  /* pulls OUT */
--bh-button-label-padding-x: var(--bh-space-xs-4);             /* pushes IN  */
```

The first is applied through `[&_svg[data-icon='inline-start']]:ms-[…]` and moves
an edge icon **toward** the button's edge. The second lives on a wrapper
`button.tsx:100` puts around every string child:

```tsx
<span data-slot="button-label" dir="auto" className="min-w-0 px-[var(--bh-button-label-padding-x)]">
```

so the label is held **away** from it. Each is defensible alone. In the ordinary
case — an icon, then a word — they compound, and the icon side ends up tighter
than the label side by the offset plus the label padding.

Measured child by child, so the arithmetic is checkable:

| | Distance from the button's edge |
| --- | --- |
| icon box | 5px — 6px padding, less the 1px offset |
| icon ink | 7.25px |
| label span | 6px, flush with the padding |
| text advance | 10px — the span's own 4px |
| text ink | 10.68px |

**Scope, stated because the same screen contains a case this does not explain.**
The `Filter` button beside it carries an icon at *both* ends and is also
asymmetric — 6.5px against 9.5px — but that one is the icon set, not the
component: `list-filter` insets its ink 1.5px inside an 18px box and
`chevron-down` insets 4.5px, and 3px is exactly the difference measured. This
entry is only about the icon-and-label case, where no label padding has a
counterpart on the icon side.

This was first dismissed as our own markup. It was ours, partly: the icons
carried a `size-` class that opted them out of both the component's sizing and
its optical offset. With that corrected to the documented `data-icon` form, and
the icons at the component's own 18px, the imbalance is still there — and now
nothing in the composition belongs to us.

## Menu

### `menu-1` · `onSelect` cannot be annotated the way Radix documents it

**File:** `menu.tsx` · **Severity:** minor · **Status:** Confirmed
**Repro:** frame `bills`, the `Filter` button. Its rows call `onSelect` and
`preventDefault()` so a multi-select menu stays open. Annotate the parameter and
the build stops.

`MenuItemProps` intersects two sources that both define `onSelect`:

```ts
type MenuItemProps = React.ComponentProps<"div"> &      // the DOM select event
  VariantProps<typeof menuItemVariants> &
  MenuItemPrimitiveProps                                // Pick<Radix.Item, "onSelect" | …>
```

`<div>` has an `onSelect` — the text-selection event, `ReactEventHandler`. Radix
reuses the name for something unrelated: a native `Event` describing the item
being chosen. Intersected, the prop resolves to

```
ReactEventHandler<HTMLDivElement> & ((event: Event) => void)
```

and a handler has to satisfy both. Radix's own signature does not:

| Written as | Result |
| --- | --- |
| `onSelect={(event) => …}` | compiles |
| `onSelect={(event: Event) => …}` | **TS2322** |

Both forms were compiled to check, rather than reasoned about. The second is what
Radix's documentation shows, and it is the one a reader arrives with; the error
it produces names `SyntheticEvent` and `cancelBubble`, neither of which appears
anywhere in the code being written.

There is a working path, so this is minor: leave the parameter unannotated and
contextual typing resolves it. It costs a reader the time it takes to discover
that the fix is to delete something.

### `menu-2` · The documented composition paints the menu under the table

**Files:** `menu.tsx`, `expanded/table.css` · **Severity:** major · **Status:** Confirmed
**Repro:** frame `bills`. Open `Filter`. The menu appears, and the table below it
paints over the lower half.

`MenuContent` renders `DropdownMenuPrimitive.Content` directly. Radix's `Content`
is inline unless a `Portal` wraps it, and `MenuContent` does not wrap one.
`MenuPortal` is exported, so the escape hatch exists — but the example in
`banhaten docs menu` does not use it:

```tsx
<MenuRoot>
  <MenuTrigger>Open menu</MenuTrigger>
  <MenuContent width="menu">      // no MenuPortal
    <MenuItem>Profile</MenuItem>
  </MenuContent>
</MenuRoot>
```

Left inline, the menu is subject to every stacking context around it. One of
them is shipped by the same package. `.ds-table-wrap` — the scroll wrapper
`Table` renders around its grid — sets `contain: paint`, and paint containment
makes an element paint atomically, as though it had `z-index: 0`.

Measured with the menu open:

| | `position` | `z-index` | `contain` |
| --- | --- | --- | --- |
| Radix popper wrapper | `fixed` | **`auto`** | `none` |
| `.ds-table-wrap` | `static` | `auto` | **`paint`** |

Neither carries a real z-index, so paint order falls to document order, and the
table comes after the toolbar. The menu loses to a sibling it has no relationship
with.

Wrapping in `MenuPortal` fixes it, and that was verified rather than assumed: the
popper wrapper becomes a direct child of `<body>`, and `elementFromPoint` at the
menu's lower edge returns a node inside the menu instead of the table.

**Why it is more than a composition note.** Both halves ship in this package,
and the failing arrangement is the documented one. A team follows the example,
puts a menu near a table — which is where menus go — and gets a broken one, with
nothing to suggest the fix is a component they were never shown.

## Across components

### `architecture-3` · An out-of-union value renders unstyled, in every component

**Files:** `select.tsx`, `badge.tsx`, and every component built on `cva`
**Severity:** major · **Status:** Confirmed
**Repro:** frame `specimens`, the row of four triggers. The last one asks for
`size="sm"` and comes back 24px tall against 32, 32 and 36.

`badge-2` reported this on `Badge`. It is not a `Badge` quirk. It is how every
component in the package behaves, and `Select` is where it does real damage.

| Asked for | Resolves to | Height |
| --- | --- | --- |
| `density="compact"` | `md` | 32px |
| `size="md"` | `md` | 32px |
| `size="lg"` | `lg` | 36px |
| `size="sm"` | `sm` | **24px** |

`Select` accepts `md`, `lg` and `comfortable`. `sm` is not among them, so `cva`
matches no rule, applies no padding class, and the trigger collapses onto its own
text. `defaultVariants` does not save it: those apply when a prop is `undefined`,
and `"sm"` is defined.

**Why `sm` in particular.** It is the most plausible wrong guess in the package,
because it is right almost everywhere else:

| Component | Does `sm` exist? |
| --- | --- |
| `Button` | Yes — `xs` `sm` `default` `lg` `xl` |
| `Table` | Yes — `sm` `lg` |
| `Badge` | Yes — `xs` `sm` `default` `lg` |
| `Select` | **No** — `md` `lg` `comfortable` |
| `Input` | **No** — `md` `lg` `comfortable` |

Five components, one prop name, three incompatible unions. A row that mixes a
button with a select is the common case, and the two do not share a vocabulary.

**How it was found, which is the part worth reading.** Not by reading source. A
designer opened the Neon frame and said the selects looked cramped, that the text
was too close to the edge. The inspector reported `150×24`. `USAGE.md` documents
the intended heights — compact 32, default 36, comfortable 40 — and 24 is none of
them. Nothing had errored, nothing had warned, and the screen had been reviewed
several times before anyone noticed.

**Why it matters.** A defect that announces itself gets fixed on the day it is
written. This one produces a control that is merely a little too short — the kind
of thing a reviewer attributes to the design rather than to a bug. It survives
review precisely because it looks like a choice.

The registry knows the valid set: `banhaten docs select` prints it. Nothing at
runtime or in the editor uses that knowledge when a value falls outside it.

### `architecture-4` · The density contract is per-control and nothing carries it

**Files:** `toolbar.tsx`, `segmented-control.tsx`, `button.tsx`, `input.tsx`,
`select.tsx`, `button-group.tsx` · **Severity:** major · **Status:** Question
**Repro:** frame `neon`, the toolbar. Every control there names its own density.
Remove `density="compact"` from any one of them and it grows to 36 beside
neighbours at 32.

`USAGE.md` states the rule as a row-level one:

> Use one semantic `density` across controls in the same row: `compact` is 32px,
> `default` is 36px, and `comfortable` is 40px.

Every control implements it. `Button`, `Input`, `Select`, `ButtonGroup`,
`SegmentedControl`, `ToolbarButton`, `ToolbarSearch` and `ToolbarSelect` all take
a `density` prop, and all of them resolve it to the documented heights. The
vocabulary is complete and consistent, which is more than most systems manage.

**What is missing is the row.** `Toolbar` accepts `density` for its own surface
and does not pass it down: there is no context in `toolbar.tsx`, no provider
anywhere in the package, and a `grep` for `createContext.*[Dd]ensity` across
`components/ui` returns nothing. So a rule written about rows is expressed one
control at a time, and every control that is not told falls back to `"default"`.

**Why that is worse than it sounds.** The failure is 4px and silent. Nothing
errors, nothing warns, and 36 beside 32 reads as slightly generous spacing rather
than as a bug. Building this toolbar we passed `density="compact"` to eleven
controls and missed three. The bar shipped with two heights in it, was reviewed
several times, and was caught by a designer noticing that one group looked
smaller than its neighbour — not by anyone reading the code.

That is the same shape as `architecture-3`: the system knows the right answer and
nothing applies it on your behalf.

**What we cannot decide for you.** A `Toolbar` that passed its own `density` to
its children would fix the toolbar case and leave the filter row, which is not a
toolbar. A context provider would cover both and is a larger change with
inheritance rules to settle. Either way it is API, and API is yours.
