# Banhaten audit: start here

Four short reports. Each one is a single story, and none of them needs the
others.

**Every entry is against Banhaten 0.4.0**, re-verified after updating from 0.3.0.
The update rewrote twelve component files, including nearly every file named
here. Nothing in this report was fixed by it.

| Report | Covers |
| --- | --- |
| **Keyboard** | `toolbar`, `button-group`. Focus management, and why it is missing |
| **Direction** | `kbd`, `tooltip`, `Table`, `Breadcrumbs`, `PageHeader`. RTL and bidi |
| **Forms** | `input`, `badge`, `checkbox`, `progress`, `select`, `avatar`, `button`, `menu`, `segmented-control`, `toolbar`. Flags that do nothing, values that fail silently, tokens wired to the wrong mode or to no theme at all, a clear button the browser draws, a control that cannot reach the icon mode it reuses, and a density rule nothing enforces |
| **Data** | `Table`, `PageHeader`, `pagination`. Counts, labels, untranslated strings |

## How an entry is named

After its component, numbered in the order we found it. So `toolbar-1`,
`badge-2`. The name carries the subject before you reach the text, and it
survives a retitle, which matters because entries cite each other.

Every entry opens with the same header line — the files it touches, a severity
and a status — followed by a **Repro** naming the frame and, where it matters,
the appearance to put that frame in.

Status is one of three:

**Confirmed.** It reproduces on a named frame, and the cause is identified in the
source.

**Question.** More than one answer is reasonable, and the choice is yours.

**Narrowing.** The entry corrects an earlier one in this report by making it
smaller. `kbd-2` is the only one, and it carries no severity, because what it
records is that a defect reaches less than we first said.

Severity is one of two, and it describes your reader's cost rather than ours:

**major.** Something reaches a person broken — assistive technology is told
nothing or told the wrong thing, text renders in an order its script does not
read, a control is invisible in a shipped theme, or a keyboard cannot drive a
component that presents itself as drivable.

**minor.** A correctness or consistency problem with a workaround, a narrow blast
radius, or a cost paid by whoever writes the code rather than whoever uses it.

## This report proposes nothing

No entry here contains a patch, a diff, or a recommended API. That is deliberate.

An audit that arrives with fixes attached asks you to review two things at once:
whether the problem is real, and whether a stranger's solution is the one you
want. The second question is easier to answer than the first, so it gets answered
first, and a rejected fix takes a real finding down with it.

So every entry stops at the same place: what happens, where to see it, and what
in the source causes it. Choosing what to do is your work, and you have context
we do not — roadmaps, consumers, and the reasons behind decisions that look
arbitrary from outside.

**"Promises" means the registry, not our reading of it.** Every entry was checked
against `banhaten docs <component>` and the RTL rules each component publishes.
Where a component declares a contract and breaks it, the entry says so. Where it
declares nothing, the entry says that instead — `kbd-1` and `breadcrumbs-1` are
the same bug mechanically, and only one of them contradicts something you wrote
down.

Each reproduction has an `-rtl` twin, and every string in it is Arabic. That is
deliberate, and it is not the same test as an RTL layout carrying English. An
Arabic interface fails on things Latin never shows: the script has no uppercase,
it needs more line height at the same size, and letter-spacing breaks its joins.

`specimens` is the other half. Its strings are Latin and stay Latin in both
directions, which is the only way to see what an RTL container does to text
running against it. Six findings have no other frame:

| | Needs |
| --- | --- |
| `table-2`, `breadcrumbs-1`, `page-header-2` | Latin text in an RTL document |
| `avatar-1` | Arabic names, which no reproduction carries |
| `badge-1` | The same colour asked for through `Badge` and through `Table` |
| `badge-2`, `architecture-3` | A value outside a component's union, which no screen passes on purpose |



Every screen except `specimens` reproduces a real product. Without that, any
defect can be answered with "that layout is not real". Where a screen needed something Banhaten does not
ship, like navigation lists or prose or page tabs, that part is plain markup. A
defect there would be ours, not yours.

## Verified good

Checked deliberately and found correct, so nobody re-checks them.

**RTL layout.** Column order, sort affordances, filter chips, the search field
and its icon, pagination controls, page header actions and breadcrumbs all
mirror. So does the browser's own clear button inside the search field, which
`toolbar-3` faults for its colour and not its position.

**Theming.** `brown` and `sharp` change brand colour and radius with nothing
hardcoded leaking through.

**Dark mode.** Status colours, row separators and surfaces hold.

**Arabic typography.** IBM Plex Sans Arabic loads and renders at table density.

**Alignment.** `align: "end"` resolves to the left edge in RTL for numerics.

**Already carrying `dir="auto"`:** `tag`, `badge`, `button`.

## Investigated and rejected

Knowing what is *not* broken keeps the rest credible.

**`Table` does not draw its own progress bar.** It defines a local `Progress`
function, which looked like a second implementation. It is a wrapper around
`components/ui/progress` with three preset props:

```ts
import { Progress as ProgressPrimitive } from "@/components/ui/progress";
```

One implementation, so no divergence is possible.

**Currency renders as `$US ١٢٬٤٨٠٫٥٠` in RTL, not `US$ …`.** Correct.
`Intl.NumberFormat("ar-EG")` emits the mark, then digits, then `US$`. The `$` is
bidi-neutral, so the Unicode algorithm places it left of `US` in an RTL
paragraph. Verified by reading the raw code points.
